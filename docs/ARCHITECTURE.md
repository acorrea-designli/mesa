# Mesa architecture

Mesa is Andrés's personal work-ops board: one place for what waits on him (GitHub PR reviews, Basecamp client requests, Slack replies, Claude's questions), a kanban mirrored to a private GitHub Project, two-way tickets with Claude Code agents, permission approvals for blocked tool calls, PR reviews, and an approval queue (Salidas) for every outgoing Slack, Basecamp or GitHub write.

Product and design sources: `PRODUCT.md`, `DESIGN.md`, `.impeccable/design.json`, `.impeccable/surfaces/src-app-page-tsx.md`, and the approved mocks in `.impeccable/mocks/screens/` (see `docs/TASKS.md` for which variant each screen uses).

## 1. Shape of the system

```
 phone ──▶ Cloudflare Access (his email) ──▶ cloudflared (this PC) + MESA_TOKEN ───────┐
 desktop browser (localhost) ──────────────────────────────────────────────────────────┼──▶ Next.js app (127.0.0.1:8790) ──▶ SQLite  data/mesa.db
                                                                                       │      ├─ RSC pages: / /tablero /tickets /salidas /telefono /kit
                                                                                       │      ├─ REST API  /api/*
                                                                                       │      ├─ long-polls /api/wait (sessions), /api/approvals/:id?wait= (hook)
                                                                                       │      └─ sweeper (1 s): undo windows, schedules, expiry, approval expiry
                                                                                       │
 lead session (MESA_SESSION=lead) ──▶ bin/mesa ──▶ REST API ◀── mesa wait
   ├─ ephemeral agents (MESA_AGENT, MESA_TICKET) ─▶ bin/mesa
   │    └─ PermissionRequest hook ─▶ scripts/hooks/mesa-approval.mjs ─▶ /api/approvals
   │    └─ PermissionDenied hook ─▶ scripts/hooks/mesa-denied.mjs ─▶ /api/approvals (kind denied)
   ├─ MCP: Slack, Basecamp (read via mesa-sweep, write only approved salidas)
   └─ engram (primary memory, topic mesa/<ref>)
 gh CLI (server side) ──▶ GitHub notifications polling, review requests, GitHub Project   [lane C]
 engram CLI (server side) ──▶ read-only memory panel                                     [lane C]
```

- **Mesa never talks to Slack or Basecamp.** Those connectors live in Claude sessions as MCP tools. There are no Slack or Basecamp tokens, apps, webhooks or OAuth routes in Mesa: Mesa holds no Slack token at all. Slack salidas go out as drafts in Andrés's own Slack composer by default (he presses send, so it is his own message, with no "Sent using @Claude" footer), or, when he picks "Aprobar y que Claude lo envíe", through the connector's `slack_send_message`, which carries the footer. Ingest for both comes from the `mesa-sweep` skill run by a session (on demand from "Barrer ahora", or a light periodic sweep by a cheap model during work hours) feeding `mesa item upsert` with a dedupe key per source item. Outgoing messages are approved salidas executed by the lead.
- **One stable lead session owns every ticket.** It runs with `MESA_SESSION=lead` (override with `MESA_LEAD_SESSION` on the server), blocks on `mesa wait`, and relays wakes to the ephemeral agents it spawns.
- **Agents are ephemeral.** No state may live only in a context window (the lead's is capped at 200k). Everything an agent needs to resume is on the ticket: brief, plan, messages, handoffs, team, approvals, findings and the engram topic key. `mesa ticket context <ref>` returns it in one payload.
- **GitHub is read server side** with the `gh` CLI (Andrés's own login): the notifications API polled honoring `X-Poll-Interval`, review requests and the GitHub Project mirror. **GitHub writes** (review approval, PR comments) are salidas with source `github`, approved by Andrés and executed by the lead.
- **Google Calendar is read server side and written by the lead** (t112). The server polls Andrés's private iCal (ICS) feed (`MESA_GCAL_ICS_URL`, a secret in `.env.local`) about every 5 minutes, read only, into `calendar_events`; Mesa holds no Google token and no OAuth. Creating an event is a salida with source `calendar`: the lead creates it through the Google Calendar MCP connector only after `salida.released`, with exactly the approved fields (hook G5). § 14.
- **Engram is the primary memory.** Every ticket thread and decision is saved to engram under topic key `mesa/<ref>` (scoped by the ticket's project) and linked in `engram_links`. Mesa only reads engram (CLI) for the memory panel.

## 3. Data model

All timestamps are ISO-8601 UTC strings. JSON columns are TEXT. Ids are `<prefix>_<12 base36>`. Tickets also get a short `ref` (`t1`, `t2`, …) used everywhere agents and `@` references name a ticket.

### Work
- **items** (`0001`): one row per thing waiting on Andrés, unique by `(source, external_id)`. That pair is the dedupe key: `pr:<owner>/<repo>#<n>`, `slack:<channel>:<ts>`, `basecamp:<recording id>`, and so on. Columns: `source` github|slack|basecamp|claude, `kind`, `title`, `excerpt`, `project`, `url`, `need`, `station` (inbox|todo|doing|waiting|done), `wait_on` (you|client|claude|none|person:<name>), `tag`, `task_id`, `meta`, `is_sample`, `received_at`, `skipped_at` (`0710`). Hoy draws items.
  - **Saltar (`skipped_at`).** "Saltar" on a Hoy row or detail pane marks an item Andrés does not want to act on: `items.skip(id)` sets `station` done, `wait_on` none and `skipped_at` now, and never touches the card (`task_id`) or a ticket. It is its own column because `meta` is replaced on every upsert. **Upsert rule:** `items.upsert` of an existing skipped item drops `station` and `waitOn` from the patch, so a sweeper or GitHub re-upsert of the same `(source, external_id)` keeps it done and skipped while title, excerpt, url and meta still refresh; a new external id (a new comment) is a normal Te espera item. The GitHub review sync leaves a skipped PR alone (no detail read, no upsert, no reopen), even if the review is requested again. `items.unskip(id, { station, waitOn })` (Deshacer) restores both and clears `skipped_at`; so does any move to a station other than done (`PATCH /api/items/:id`, the card move, the Project pull). In Hecho a skipped item reads "Saltado".
- **tasks** (`0001`): kanban cards on Tablero. `source` is the card's lane (Tablero B), plus `station`, `wait_on`, `position`, and the GitHub Project mapping `gh_item_id`, `gh_content_url` (always null since `0320`: the mirror holds drafts only), `sync_state` synced|pending|error|local, `sync_error`, `synced_at`. Items link with `items.task_id`; moving a task moves its items. `ticket_id` (`0500`) is the ticket Claude works the card in ("Dárselo a Claude"); null for a note-only card. The repository fills `owner` (`TaskOwner`: `ticketRef`, `ticketStatus`, and the live owner agent from `ticket_team`, null until the lead spawns one) for the owner chip. Project ids live in `settings` (`gh_project.*`, written by lane C). Station ↔ Status: Inbox, Todo, In Progress, Waiting, Done.
- **ignored_projects** (`0400`): projects Andrés chose to ignore ("Ignorar proyecto «X»"). Columns `source` (one of the four, or `*` for every source), `project` (the project key), `label` (what «X» reads), `created_at`; unique `(source, project)`. The project key is the most specific stable id, read from the dedupe key by the generated column `items.project_key` (mirrored by `projectKey()` in `src/lib/domain/ignore.ts`): GitHub `owner/repo` (from `pr:<owner>/<repo>#<n>`; `items.project` is the bare repo name), Slack the channel id (the segment before the last `:` of `<channelId>:<ts>`), Basecamp the project name, Claude the project. A row matches an item when the source is the same (or the row is `*`) and the row's project equals the item's key or its plain `project`; a task matches by its own `project` or by a linked item of its lane's source (a GitHub task made from Hoy carries the bare repo name, its PR item carries `owner/repo`).
  - **Filtered by query, never flagged or deleted.** `items.list({ ignored: "exclude" })`, `tasks.list({ ignored: "exclude" })` and `counts()` leave them out, so they leave Hoy, the band, the rail counts and the Tablero; deleting the row brings them all back as they were. The ingest never upserts them: the GitHub review search skips them (and leaves their existing items alone instead of moving them to Hecho), `POST /api/items/upsert` answers `{ ignored: true }` without storing, and the sweeper reads `mesa ignore list` each tick and skips them before triage. `tasks.pendingSync()` skips them, so the GitHub Project is not written. Salidas and tickets are never filtered: a pending salida of an ignored project stays in Salidas.

### Tickets and agents
- **tickets** (`0001`): `ref`, `direction` (claude_asks|andres_asks), `title`, `status` (§4), `project` (engram scope), `owner_session` (normally `lead`), `item_id`, `task_id` (`0500`, the board card it works; `tasks.ticket_id` points back), `woke_at`, `closed_at`, and since `1040` (t126) `pause_reason`, `paused_until_ticket_id` (soft link to the ticket a paused one waits for, cleared if that ticket is deleted) and `paused_at`, all set only while the status is `paused`/`ongoing` and cleared when it leaves them. Engram topic key: `mesa/<ref>` (`ticketTopicKey`).
  - **ticket_messages**: `author` andres|claude, `body` (Markdown), `options`, `recommended`, `recommendation` (legacy: NULL since `0920`, the questions live in `ticket_questions`), `chosen` (Andrés's key when his message answered exactly one question with a pick), `kind` (`0700`: `permission_request` for the "Pídeme permiso" message, else NULL), `about_message_id` (the latest Claude message at that moment).
  - **ticket_questions** (`0920`): a Claude message's question card, one row per question: `message_id`, `n` (step, from 1), `text` ('' on a 1-step card whose message body is the question), `options` (`[{key,label,detail}]`, 2-6, keys A-F), `recommended`, `recommendation`, `state` open|answered|withdrawn, `chosen`, `answer_text` (his own words), `answer_message_id`, `answered_at`, `withdraw_reason`. 1-6 questions per message (`cardProblem`). A question stays open until Andrés answers it or Claude withdraws it; a later message, plan, note, card or reply that answers something else never closes it. Closing the ticket withdraws the open ones ("Ticket cerrado"). `0920` back-filled every old options message as a 1-step card: answered (with `chosen`) when Andrés wrote after it, withdrawn when nobody did and the ticket is closed, else open.
  - **ticket_steps** (`1020`, t124): a Claude message's checklist, one row per step: `message_id`, `n` (from 1), `text` (one line, at most 300), `detail` (optional Markdown, at most 4000), `state` open|done, `done_by` andres|claude (NULL while open), `done_at`, `note` (Claude's one-line verification, only on a step Claude marked). 1-30 steps per message (`checklistProblem`); several checklists per ticket. A CHECK keeps `state`, `done_by` and `done_at` consistent. Anyone sets a step either way, any number of times; nothing else changes it (a later message, a reply, closing the ticket). A checklist is not a question card: it does not count against "one open card per ticket". `TicketDetail.checklists` and `TicketContext.checklists` group the steps by message with `done` / `total` / `allDone`.
  - **attachments**: files under `data/uploads/<ticket id>/`.
  - **annotations** (`1030`, t125): Andrés's marks on a ticket's PDF attachment, `author` andres|claude. `page` (from 1), `kind` highlight|note|rect|ellipse|arrow, `geometry` (JSON in **page units**: the page's viewport at scale 1, i.e. PDF points, origin top left, y down, so it lines up at any zoom; `highlight { rects: [{x,y,w,h}] }`, `note { x, y }`, `rect|ellipse { x,y,w,h }`, `arrow { x1,y1,x2,y2 }`), `quote` (the selected text of a highlight), `body` (the comment), `state` open|resolved, `sent_at` (when it went to Claude in a `ticket.annotations` wake; NULL = not sent yet, and an edit, a reopen or a new reply by Andrés clears it again). The API adds `rect`, the bounding box of the geometry, and `replies`; lists are in reading order (page, top to bottom, left to right).
  - **annotation_replies** (`1030`): `annotation_id`, `author` andres|claude, `body`, `created_at`.
  - **ticket_refs**: `@` references (`ticket`|`item`|`url`).
  - **planned_actions**: the "Claude va a hacer" plan: `seq`, `kind`, `source` (line colour), `label`, `mode` direct|needs_ok, `state`, `target`. Anything that writes outside Mesa (Slack, Basecamp, GitHub) is a salida, never a direct action.
- **ticket_briefs** (`0002`): the living summary, one per ticket, rewritten by the owner on every milestone: `body` (Markdown), `goal`, `decisions[]`, `plan_step`, `open_questions[]`, `next_action`, `revision`, `updated_by`.
- **ticket_handoffs** (`0002`): append-only checkpoints: `agent`, `role`, `status` done|paused|blocked, `body`, `done`, `remaining`, `artifacts` (`{branch, pr, files[], …}`).
- **ticket_team** (`0002`): agents attached to a ticket: `name` (PK, `<role>-<ticketRef>[-k]`, never reused), `role`, `owner`, `status` live|retired (the API values for "alive" and "spent"), `spawned_at`, `retired_at`.

### Approvals and reviews
- **approvals** (`0002`): permission requests from the hook: `ticket_id` (NULL → shown on Hoy), `agent`, `tool`, `summary` (file or command description), `detail` (diff or exact command), `cwd`, `hints[]` (closest allow rules), `status` pending|decided|expired, `decision` allow|read_config|deny, `note`, `decided_by`, `decided_at`, `expires_at`; since `1060` (t128) `kind` permission|denied, `reason`, `denied_input` and `rule` for the auto-mode denial card (§7b).
- **reviews** (`0002`): one per PR (`repo`, `pr` unique), `ticket_id`, `head_sha` (the reviewed head), `state` open|approving|approved|closed (`closed`: `1010`), `salida_id` (the approve write), `close_reason`, `closed_at` (`1010`).
- **review_findings** (`0002`): `n` (stable within the review), `label` blocker|nit|comment, `at` (`path:line`), `anchor` (code excerpt), `summary`, `explanation`, `state` open|fixed|waived|dismissed, `sha`, `gh_comment_id` (set by the lead after posting), `salida_id` (the post write).

### Salidas
- **salidas** (`0001`): `status` (§4), `source` slack|basecamp|github|calendar (`1000`), `destination` JSON, `title`, `context`, `ticket_id`, `links`, `owner_session`, `current_version`, `approved_version`, `send_mode` (`0900`: Slack only, `draft` default | `send`, set with the approval or Programar, cleared by an undo; null for every other source), `undo_until`, `released_at`, `send_at`, `expires_at`, `drafted_at` (`0900`), `sent_at`, `permalink`, `error`, `delete_requested_at`, `deleted_at`, `withdraw_reason`, `withdrawn_at` (`1010`).
  - Destination kinds: `slack_thread|slack_channel {workspace, channel, channelId?, threadTs?, threadLabel?, postAs}`; `basecamp_comment|basecamp_campfire|basecamp_message {project, projectId?, recordingId?, recordingTitle?, postAs}`; `github_review {repo, pr, event APPROVE|COMMENT|REQUEST_CHANGES, commitId?, postAs}`; `github_comment {repo, pr, path?, line?, commitId?, findingN?, postAs}`.
  - `calendar_event {calendar, invitees?, meet?, postAs}` (t112): where a Google Calendar event goes. The event's fields are the approved version's body, one per line (`Título`, `Inicio`, `Fin`, `Zona`, `Invitados`, `Meet`, `Descripción`; `src/lib/domain/calendar-event.ts`), so editing the text edits the event (the destination's `invitees` and `meet` are rewritten from the current version's body on every new version and "Volver a vN", so the chips never go stale); `create` and every new version refuse a body that is not a complete, valid event (400). `DELETE_POLICY` is none (Mesa never deletes events).
  - Delete policy (`DELETE_POLICY`): Slack none (a direct send: the undo window is the only way back; a Slack draft is Andrés's to delete in Slack), Basecamp comment/message trash (restorable 25 days), Campfire permanent, GitHub review none, GitHub comment permanent.
  - **salida_versions** (immutable, `n` from 1, `author` claude|andres, `turn_id`, `starred`), **salida_turns** (refine chat; Andrés turns carry semáforo `marks`; an open turn blocks approve), **learned_chips** (labels from Andrés's own requests, top 4).

### Plumbing
- **sessions**: `id`, `label`, `cwd`, `project`, `cursor`, `waiting_since`, `last_seen_at`. Unknown owner ids are registered on first use.
- **wake_events**: `id` (cursor), `session_id` (NULL = any), `kind`, `entity_type`, `entity_id`, `payload`.
- **source_state** (`0002`): one row per source (github|github_project|slack|basecamp|engram|calendar (`1000`)) holding sweep state and health: `watermark` (opaque per source: Slack ts, Basecamp updated_at, GitHub Last-Modified), `last_checked` (last probe), `last_new_at` (last probe that found something new), `backoff_until`, `cadence_s` (current probe interval, default 60), `error_count`, `last_error`, `health` ok|degraded|down, `note` (`0003` renamed `last_checked_at` and added the error fields). The sweeper reports Slack and Basecamp, and the server reports GitHub (lane C). Health feeds the Estados B rail notice and drives "Aprobar al volver".
- **settings** `last_interaction_at`: stamped whenever Andrés acts in the UI. That covers answering a ticket, approving a plan, any salida decision, refine or edit, deciding an approval, a review action, moving a card (single or batch, and its Deshacer), "Dárselo a Claude" and "Barrer ahora". Claude's writes never stamp it: `bin/mesa`, the hooks, the statusline and `sweep-tick.mjs` send `x-mesa-client: cli` on every request, and `route()` (`src/lib/api/http.ts`) runs a marked request inside `asCliCall` (`src/lib/repo/interaction.ts`), so `touchInteraction` is a no-op on every path it guards. The header changes nothing else (no auth or permission effect). The sweeper reads `lastInteractionAt` for its cadence.
- **engram_links**: `entity_type`, `entity_id`, `project`, `topic_key`, `observation_id`. **settings**: key/value.
- **settings** `usage.snapshot`, `usage.history` and `usage.tokens` (t45, t60, no migration): the latest statusLine snapshot (`capturedAt`, `sessionId`, `model`, `fiveHour`/`sevenDay` as `{ usedPercentage, resetsAt }`, newest capture wins) and the transcript scan state (`files`: byte offset, role and last message id per transcript; `days`: Bogota day to `<role>|<model>` to the four token counts, 14 days kept). `usage.history` (t60) is the plan % over time, `[{ t, fiveHourUsed, sevenDayUsed }]` oldest first, one point per accepted snapshot and at most one per 5 min, pruned to 8 days.
- **calendar_events** (`1000`, t112): one row per OCCURRENCE of a meeting in Andrés's Google Calendar, read only. `uid` (the ICS UID) and `occurrence_key` (the occurrence's original start, UTC) are unique together and `id` (`ce_…`) is a hash of both, so a re-read keeps the id of a meeting that did not move; a moved occurrence keeps its key and changes `starts_at`. Columns `title`, `starts_at`, `ends_at` (UTC ISO; all-day: Bogota midnight to Bogota midnight), `all_day`, `time_zone`, `location`, `meet_url`, `attendees` (JSON `[{ email, name, response }]`), `attendees_count`, `organizer`, `response` (Andrés's own PARTSTAT: accepted|declined|tentative|needs_action|none), `status` (confirmed|tentative; cancelled events are not stored), `recurring`, `is_sample`, `fetched_at`. Every poll replaces the non-sample rows in one transaction over a window of 13 weeks back to 26 weeks ahead of today in Bogota (t127: `STORED_BACK_DAYS` 91 and `STORED_AHEAD_DAYS` 182 in `src/lib/domain/calendar.ts`, re-exported as `WINDOW_BACK_DAYS` and `WINDOW_AHEAD_DAYS` by `calendar-worker.ts`; about 500 rows); the seed owns the sample rows. The event link is not stored: it is built when the payload is read (§ 14, `GET /api/calendar`). The feed address is stored nowhere.
- **push_subscriptions** (`0910`): one row per device that turned phone notifications on: `endpoint` (unique), `p256dh`, `auth`, `label`, `user_agent`, `created_at`, `last_ok_at`, `last_error`. A send answered 404/410 deletes the row. The push notifier keeps its seen keys and last scan time in **settings** (`push.seen`, `push.last_scan`).

## 4. State machines

### Salida

```
draft ─propose─▶ pending ─approve(vN)─▶ sending ─(20 s)─ release ─▶ sending·released ─sent─▶ sent ─request_delete─▶ … ─deleted─▶ deleted
                  │  ▲ ▲  │                │                               │   │                                        └─request_restore/restored (trash only)
                  │  │ └──┼──── undo ──────┘ (only inside the window)      │   └─failed─▶ failed ─retry─▶ pending
                  │  │    │                                                 └─hold─▶ queued_until_back
                  │  │    │      Slack, mode draft: sending·released ─drafted─▶ draft_created ─confirm_sent ("Ya lo envié", Andrés)─▶ sent
                  │  │    └─approve while the source is down ──────────────────────▶ queued_until_back ─resume (source back)─▶ sending·released (re-check thread)
                  │  │                                                                   ├─unqueue─▶ pending
                  │  │                                                                   └─bounce (thread changed)─▶ pending
                  │  └──unschedule── scheduled ◀──schedule(at, vN)──┘   scheduled ─(send_at)─ release ─▶ sending·released
                  ├─deny─▶ denied        (also from draft, scheduled, queued_until_back)
                  ├─withdraw {reason}─▶ withdrawn   (the lead's cleanup; pending or draft only; final, never sent)
                  └─expire─▶ expired     (pending past expires_at)
```

Rules (`transitionSalida`, tested in `salida-machine.test.ts`):
- Approve sends the version shown (`approve.version` must equal `current_version`) and is refused while a refine turn is open.
- `approve` sets `undo_until = now + 20 s`, and `undo` works only inside the window. The sweeper releases the salida when the window ends and wakes the owner with `salida.released`. **The lead sends only after that event**; `sent`/`failed` before release are refused (409).
- **Aprobar al volver.** If the source is reported down when Andrés approves, the salida goes straight to `queued_until_back` (`salida.queued` wake). If the lead finds the source down at send time, it calls `hold`. When the source is reported `ok` again, every queued salida of that source is resumed: released with `recheckThread: true`. The lead re-reads the thread first; if there are new messages it calls `bounce {reason}`, which returns the salida to pending for a fresh approval.
- **Slack send modes.** `approve` and `schedule` take `mode` for a Slack salida only (omitted = `draft`; any other source refuses one with 409): `draft` = "Aprobar", `send` = "Aprobar y que Claude lo envíe" (the card says next to the button that it goes out with "Sent using @Claude"). The mode is stored on the salida with the approval (`send_mode`), kept through release, hold and resume, cleared by an undo, unschedule, unqueue, bounce, retry and deny, and carried in the `salida.released` payload (`mode`) and in `mesa salida show` (`sendMode`). No session can set it: the approve call is Andrés's click (G10). Programar records a mode too (default draft).
- **Draft state.** For a `draft` salida the lead calls `slack_send_message_draft` and then `drafted` (`mesa salida drafted <id>`, lead only, G4 for teammates; sandbox needs `--simulated` like `sent`): status `draft_created`, shown as "Borrador en Slack · envíalo tú", distinct from sent. Only Andrés closes it with "Ya lo envié" (`confirm_sent`, his click; G10). `draft_created` never counts as sent, never re-releases and is not time-driven. A refused draft call is `hold` (never a switch to `slack_send_message`).
- **Withdraw (the lead's cleanup of stale leftovers, t123).** `mesa salida withdraw <id> --reason R` (`POST /api/salidas/:id/transition { type: "withdraw", reason }`) takes a `pending` or `draft` salida to the final status `withdrawn`; any other status is 409, a missing or blank reason is 400 (CLI exit 2). It is not a deny: it never sets `approved_version`, `send_mode`, `undo_until` or `released_at`, never emits `salida.released` or `salida.denied`, never calls `tickets.andresActed` and never stamps `last_interaction_at`. The reason and time live in `withdraw_reason` / `withdrawn_at` (migration `1010`), come back in `mesa salida show` and the API, and the card reads "Retirada · <reason>" with no approve or deny controls. Nothing leaves `withdrawn` (approve, schedule, release, sent, drafted, retry, resume, undo and the sweeper all refuse or skip it). It leaves Por firmar, the pending counts, push collect and `ticketNeeds`, and stays in today's decided strip. `mesa salida propose --wait-release` treats it as final (exit 3, "do not send it"). Withdrawing a github review salida clears `finding.salida_id` on the findings that point to it (so they can be posted again), and a review `approving` on it goes back to `open`. Deny keeps no CLI verb: it stays Andrés's click. Lead only: G4 blocks teammates.
- `schedule` needs a future time; at `send_at` the sweeper releases it.
- `request_delete` follows the destination policy.

Tablero: the card follows (`TASK_STATION_OF`: paused → Esperando, ongoing → En curso) and the owner chip reads "En pausa · hasta t125", "En pausa" or "En proceso" (with the agent in front when there is one, never "Claude · por asignar"). Tickets screen: neutral outline tags (not solid ink, not Claude orange), a tab "En pausa" listing paused and ongoing tickets (they also stay in "Abiertos"), the reason in the row excerpt, and under the thread title the reason, a link to the until-ticket and "Reanudar" (or "Pausar", a reason and an optional ticket ref; "En proceso" is Claude's alone). ### Dispatch: tasks go straight to an agent

`src/lib/repo/dispatch.ts`. Every way Andrés creates a task hands it to Claude unless he ticks "Solo anotar (sin agente)": Tablero "+ Tarea" and `mesa task create` (`POST /api/tasks`), Nuevo pedido (`POST /api/tickets` with `andres_asks`, which also creates the card on the Claude lane). "Dárselo a Claude" (`POST /api/tasks/:id/dispatch`, or `action: dispatch` in the batch) does the same for an existing card, including cards of ingested items. Handing a card to Claude creates, in one transaction, an `andres_asks` ticket owned by `lead`, linked both ways (`tickets.task_id`, `tasks.ticket_id`), sets the card's `wait_on` to `claude`, and emits one `ticket.created` wake `{ ref, ticketRef, taskId, kind? }` (`kind` review|request|investigation|reply: given, or `review` when the card links a GitHub PR). Rules: idempotent (a card with an open ticket returns it, `created: false`, no second wake; a closed ticket lets it dispatch again); sample cards are refused (409; skipped in a batch); cards created from ingested items (`itemIds`, e.g. Hoy "Crear tarea") never auto-dispatch; dispatching writes only to Mesa, nothing goes to Slack, Basecamp or GitHub.

**Batches and grouping.** Handing 2+ NEW cards to Claude in one call (Tablero "Dárselas a Claude", `action: dispatch`; Hoy "Abrir tarea y pasar a Claude", `action: dispatch_items`, which first makes the card of every item that has none the way "Crear tarea" does) opens exactly the same tickets, one per card, but suppresses their `ticket.created` and wakes `lead` ONCE with `ticket.batch { batchId: "bt_…", origin: hoy|tablero|cli, tickets: [{ ticketRef, taskId, title, kind?, urls }] }` (`entityId` = the first new ticket; existing and sample cards are never listed; the response carries `batchId`, null when no batch wake was sent). Exactly one new ticket keeps the plain `ticket.created`; none wakes nobody. The lead then groups same-topic tickets: `mesa ticket fold <primary> <ref>... --why W` (`POST /api/tickets/:id/fold`, one transaction) re-points every card of the folded tickets to the primary (`tasks.ticket_id`) and moves it to the primary card's station, copies their refs to the primary (deduped by target) plus a ticket ref to each, posts ONE informational message on the primary ("Agrupé: t25 «título», … porque W", no status change), and closes each folded ticket with "Agrupado en tN: W" and a ticket ref to the primary (label `Agrupado en`, which is how unfold knows) with no wake and no card move; 409 on a closed, sample or `claude_asks` ticket, or when `from` holds the primary. `mesa ticket unfold <primary> <ref>` (`POST /api/tickets/:id/unfold`) undoes one: the ticket reopens unclaimed, its original card (`tickets.task_id`) points back at it, both tickets say so ("Separé tN de este ticket" / "Separado de tM"), and the lead gets `ticket.created { ref, ticketRef, taskId, kind?, splitFrom }`; 409 when it was not folded into that primary. The card follows the ticket on every status change: all cards with `tasks.ticket_id = T` move (plus `tickets.task_id` while that card has no ticket or points at T), so a primary moves its grouped cards and a folded ticket moves none. No migration: fold lives in `tasks.ticket_id`, `ticket_refs` and messages.

**PR intake** (t107, `src/lib/repo/intake.ts`). The only ingested items that dispatch on their own. (1) `syncReviewRequests` hands `r.intake.reviewItems` every item it created or brought back from Hecho with a moved `updated_at` (a re-request); items already open are never back-filled. Each PR gets ONE ticket: found by the review row (`lower(repo)` + `pr`, a folded ticket stands for its primary), then by any item on a card whose key or address is the PR; an open ticket wins over a closed one. Found: the item joins its card and a closed ticket reopens (`ticket.reopened { ref, repo, pr, reason: "review re-requested" }`). Not found: a card titled `<owner/repo>#<n> · <author>: <title>` (or the PR's card without a ticket) is dispatched through `dispatch.dispatchAuto` with `kind: review` and the ticket title `Review <card title>`: one `ticket.created`, or one `ticket.batch { origin: "github" }` for 2+. (2) `POST /api/items/upsert` goes through `r.intake.upsertItem`: a Slack item with `meta.pr` (`owner/repo#n` or a PR address) is linked to the PR's ticket (created as above, origin `slack`, with a GitHub item under the same `pr:<owner>/<repo>#<n>` key, matched case-insensitively by the sync), gets `meta.ticketRef`, `meta.prTicketId` and `meta.prIntake { at, ticketCreated, reopened, verdict: null }`; a closed ticket reopens quietly, the ticket gets one `tickets.note` line (Claude, no status change, no wake) and its owner session ONE `ticket.pr_message`. Mesa never classifies (`meta.intent` is ignored): the writer on the ticket does. A notice: `r.intake.prNotice` (`POST /api/items/:id/pr-notice`, `mesa item pr-notice`) sets `prIntake.verdict: "notice"`, moves the item to Hecho with `waitOn: none`, writes one more line, creates no salida, and closes the ticket again (by claude, no wake) when this message had reopened it and no other linked message without a verdict nor a live salida is on it; idempotent, 409 for an item that is not a linked Slack PR message. A question: the item stays until a Slack salida of that ticket to the same channel and thread ends `sent`, `denied` or `expired` (`settlePrQuestions`, called from `salidas.transition`, settles every linked item whose verdict is not notice). A re-upsert of a handled `externalId` refreshes the content only and keeps station, `waitOn` and the link. The repo of an ignored project or a PR item he skipped never gets a ticket this way. Switch: `autoDispatch` in `config/sweep.json`, `MESA_AUTO_DISPATCH` overrides it (`autoDispatchEnabled`).

### Approval

`pending` → `decided` (allow | read_config | deny) by a decision before `expires_at`, or → `expired` at `expires_at` (lazily and by the sweeper). Decisions are final: a second decision, or any decision after expiry, is refused (409). Only `allow` lets the call run.

### Review

`open` → `approving` when Approve / Approve anyway creates the approve salida → `approved` once that salida is sent; back to `open` if it is undone, denied, failed, expired or withdrawn. `open` → `closed` when the lead runs `mesa review close <id> --reason R` on a stale card (see § 6); `review open` reopens it. Findings go from `open` to one of: `fixed` (set by the reviewer on a new head), `waived` (Approve anyway) or `dismissed` (Dismiss).

## 5. Ephemeral agents and the resume payload

- **Naming:** `<role>-<ticketRef>[-k]` (`dev-t17`, `review-t17-2`). `POST /api/team` refuses a name that was ever used.
- **Lifecycle:**
  1. The lead adds the agent (`mesa team add`) and starts it with `MESA_AGENT` and `MESA_TICKET` in its environment and `MESA_SESSION=lead`.
  2. The agent starts with `mesa ticket context <ref>`.
  3. While it works, it rewrites the brief on every milestone (`mesa ticket brief`).
  4. Before it stops, it records a handoff (`mesa handoff … --status done|paused|blocked`).
  5. The lead retires it (`mesa team retire`).
- **Resume payload** (`GET /api/tickets/:ref/context?messages=20`, `TicketContext`): `ticket`, `brief`, `plan`, `messages` (last N, oldest first), `openQuestions` (brief questions plus one `"<tq id> · <n>. <text>"` line per open question row), `questions` (every question of the ticket with its state, answer and withdraw reason), `checklists` (every checklist with its steps: `state`, `doneBy`, `note`, plus `done` / `total` / `allDone`), `team`, `handoffs` (latest per agent), `latestHandoff`, `approvals` (pending), `salidas` (not final), `findings`, `engram {topicKey: "mesa/<ref>", project, links}`.
- **Memory:** after each milestone the owner saves the thread and decisions to engram under `mesa/<ref>` (MCP `mem_save` with that `topic_key`) and links the observation with `mesa engram link`.

## 6. Reviews

The reviewer agent first opens the review with `mesa review open <ref> --repo owner/name --pr N --sha <head>` (`POST /api/tickets/:id/reviews`; the sha is required, the call is idempotent, a new head reopens an approved review), so a clean pass with zero findings still gets its card with Approve. It then upserts findings with `mesa finding upsert <ref> --json -`, keyed by `repo`, `pr` and `n`. Andrés's buttons call `POST /api/reviews/:id/actions`:

| Action | Effect | GitHub write |
| --- | --- | --- |
| `approve` | refused while open blockers exist | github_review APPROVE salida |
| `approve_anyway` | waives every open finding | github_review APPROVE salida |
| `post {findingNs}` | the chosen findings become inline comments; each text is the summary plus the explanation, as shown on the card | ONE github_review salida per decision (REQUEST_CHANGES when any posted finding is a blocker, else COMMENT), with `destination.comments[]` |
| `dismiss {findingNs}` | finding → dismissed | none |
| `explain {findingNs}` | asks the reviewer for more | none |

GitHub salidas may have an empty body only for an APPROVE review (pr-review approves with no comment) or a batched review whose text lives in `destination.comments[]`. `inReplyTo` (a comment id) on the destination or on a comment makes the reply land in the existing review thread.

The button press is the approval of the exact text and destination shown on the card. The salida is therefore created already approved and enters the 20 s undo window. Every action wakes the ticket owner with `review.action {action, repo, pr, findingNs, salidaIds, note, ticketRef}`. After sending, the lead records the comment id with `mesa finding upsert` (`ghCommentId`).

**Closing a stale card (the lead's cleanup, t123).** `mesa review close <reviewId> --reason R` (`POST /api/reviews/:id/close { reason }`, its own route: `/actions` stays Andrés's buttons) moves an `open` review to `closed` and stores `close_reason` and `closed_at`; the findings are kept. An `approving` review is refused (409: a salida is in flight; withdraw it first and the review goes back to `open`), as are `approved` and an already `closed` one (409, not a no-op, so a double close shows). Review actions (approve, approve_anyway, post, dismiss, explain) on a closed review are 409. The card reads "Cerrada · <reason>" with no buttons. Its ticket leaves Te espera: `ticketNeeds` no longer lists "Decidir review", and a `waiting_andres` ticket with no other need (pending salida, permission, open question, planned `needs_ok` step, another open review) moves to `waiting_claude` through `tickets.andresActed` (no wake, not his interaction). `mesa review open` at any head reopens a closed review to `open`; the GitHub poll (`noteHead`) never reopens the review by itself, it may still reopen a closed ticket as before. Lead only: G4 blocks teammates. Cleanup recipe for a stale PR card: `mesa salida withdraw <id> --reason R` for each pending salida of the PR, then `mesa review close <id> --reason R`.

Browser notifications (`src/features/notify/`, no server part): the `Notifier` mounted in `AppShell` listens to `/api/stream` (`useLive`, ticket, salida, review, approval, item; its 5 s poll fallback too) and re-reads `GET /api/tickets?status=waiting_andres`, `/api/salidas?status=pending`, `/api/approvals?status=pending` and `/api/items?open=you` (t63: Hoy items that are not done and wait on Andrés, samples and ignored projects left out by the server), because frames carry no state. The pure `decide()` turns that set plus the seen keys into the notifications to show (`ticket:<id>` while it waits, `salida:<id>:v<n>`, `approval:<id>`, `item:<id>` while the item is open and waits on him), so an undo (same version), a reload or a second tab never repeats one. The seen keys live in localStorage (bounded); every tab scans on its own pokes under a `navigator.locks` lock on the seen keys, so each entry is shown once even when one tab's stream is down, and none is shown while a visible, focused tab is looking. A tab also stores the time of its last scan: a load within 10 minutes of it (a reload, the hard reload after a Mesa restart) starts with a normal scan, an older or missing record (first enable, long-closed browser) with a silent baseline. Each banner closes itself after 10 s (t38; `requireInteraction: false`, Mesa keeps the item) and the tab that shows a batch plays one WebAudio sound per batch (`chime.ts`, unlocked by the first click or key press of the tab) unless the rail switch "Sonido" is off (`mesa.notify.sound`, default on): the "Hoy" sound when the batch has a Hoy arrival, the short two-note chime otherwise (t63, scope "Hoy only"). When Mesa's sound started the banners are created `silent: true`; with Sonido off or audio blocked the OS sound plays. "Probar sonido" next to the Sonido switch plays the Hoy sound from a click, which also unlocks audio. The permission is asked only from the rail control "Activar avisos".

Hoy arrivals (t63): `itemWaiting()` makes the entry `item:<id>`, title "Nuevo en Hoy · <Slack|Basecamp|GitHub>", body the item title, url `/`. The key is episodic like `ticket:`: it is dropped from `seen` when the item stops being open-and-waiting, so a PR whose review is re-requested notifies again while a sweeper content refresh of an item that never left does not. `decide()` batches several arrivals of a scan into one entry ("<n> nuevos en Hoy", body "Slack 2 · GitHub 1", key and tag `mesa-hoy`). The first read of Hoy items (no `hoy:ready` marker in `seen`; both collectors pass `hoy: true`) is a silent baseline, so what is open when this ships never notifies; baseline, quiet and sandbox rules are unchanged. The sound is defined once in `hoyTone.ts` (an original 1.8 s rising bell motif: G4 C5 E5, a long G5 with a soft C6, each note a fundamental plus two overtones with an exponential decay): `chime.ts` plays it with oscillators and `scripts/render-hoy-tone.mjs` (`pnpm tone:render`, deterministic) renders the same parameters to `public/sounds/mesa-hoy.wav`; a test fails when the committed file is stale.
Web Push (`src/lib/push/`, t33): the same notifications on the phone with the app closed. `startPushNotifier()` (from `src/instrumentation.ts`; never in the sandbox, and only when `MESA_VAPID_PUBLIC_KEY`, `MESA_VAPID_PRIVATE_KEY` and `MESA_VAPID_SUBJECT` are set; `pnpm push:keys` prints a pair, nothing is written to the repo) subscribes to `subscribeChanges`, debounces 400 ms and also ticks every 30 s. Each scan (`scanOnce`) reads the waiting set from the repositories (`collect.ts`: tickets `waiting_andres` with the open-review check, salidas `pending` with the own-version check, approvals `pending`), builds the entries with the desktop builders (`ticketWaiting`, `salidaWaiting`, `approvalWaiting`) and runs the same `decide()`. Hoy items (t63) join the set (`r.items.list({ open: "you", includeSamples: false, ignored: "exclude" })`; the TYPES it pokes on include `item`; `decide({ hoy: true })`). Their entries carry only "Nuevo en Hoy · <Source>" and, for a scan with several, "<n> nuevos en Hoy": one push per scan under the tag `mesa-hoy`, never an item title, person or text. Seen keys and the last scan time persist in SQLite, so a restart within 10 minutes (`shouldBaseline`) scans normally and an older one is a silent baseline: a long-down server never floods. Quiet rule as on the desktop: while any Mesa tab (desktop or phone) beats `POST /api/push/looking` (8 s lifetime, in memory) nothing is sent and the keys are remembered. The payload is `{ title, url, tag }` only (a meeting reminder also carries `body`, see "Meeting reminders" below): the title is the kind and ref (`Te espera · t33`, `Review lista · t33`, `Por firmar · t33` or `Por firmar · salida`, `Permiso pendiente · <agent>`), never a ticket or salida title, message text or repo name. It is sent with `web-push` (VAPID, TTL 12 h, urgency high) to every row of `push_subscriptions`; the seen keys are saved before sending, so a crash never repeats a push; 404/410 deletes the subscription. Phone side (`src/features/push/`): `usePush.ts` is one shared store (the `/telefono` card "Avisos en este teléfono" and the "Ajustes" row `PushRow`, which replaces the desktop notification toggle on the phone) whose state comes from the pure `state.ts` (on, off, blocked with the browser's unblock steps, unsupported, iOS "install first", no keys, no worker). The permission is requested through the service worker registration (`pushManager.subscribe` straight from the tap), the path that works on Android Chrome and Opera; `PushSync` (in `AppShell`) re-syncs the subscription with `POST /api/push/subscription` on every page load (an upsert, so a worker re-POST blocked by Access is repaired; a subscription made with other VAPID keys is dropped and made again) and beats `/api/push/looking` every 3 s while the tab is visible and focused. `public/sw.js` handles `push` (title and tag from the payload, a fixed Spanish body, no fetch; with a tag it sets `renotify: true`, so a newer `mesa-hoy` push alerts again instead of replacing the old one silently), `notificationclick` (focus and navigate an open Mesa window, else `openWindow`) and `pushsubscriptionchange` (re-subscribe and re-POST, best effort). A device with a usable subscription sets `mesa.push.device` in localStorage and the in-page `Notifier` stays silent there, so one device never gets both. Phone sound: Web Push cannot choose a sound (the `sound` option exists in no browser; `vibrate` is ignored on Android 8+). Android plays the notification-channel sound of the browser or installed PWA, which Andrés can change in Android settings (a custom audio file is allowed), so the `/telefono` card shows "Descargar tono" (`/sounds/mesa-hoy.wav`, behind the same token as the rest) and three steps to set it. Opera Android may keep one channel for all its sites, so the tone can apply to every Opera notification; iOS only has on/off.

Meeting reminders (t112, decisions 5A and 6C): ten minutes before a meeting, a desktop notification and a phone push. A meeting is a stored event that is timed (not all-day) and not declined by Andrés (`response` is not `declined`; sample events never notify). `remindersDue()` (`src/lib/domain/calendar.ts`) lists those whose start is within `REMIND_MINUTES` (10) and not yet reached, so a scan that runs late still reminds until the start. The key is `meeting:<event id>:<start>`: once per event start, and a moved start is a new key that notifies again. It reuses the whole pipeline (`decide()`, the seen keys, the in-page notifier and the server push notifier) with three differences. (1) It bypasses the quiet rule and the first-scan baseline: a meeting in ten minutes is shown even while a Mesa tab is focused. (2) It is time-driven: the in-page engine rescans every 30 s (and reads `GET /api/calendar` for today and tomorrow; a calendar that cannot be read means no reminders, never a failed scan), the server notifier already ticks every 30 s and reads the repository. (3) **It carries the meeting's title, the one exception to the t33 rule that a push carries no titles**: the notification title is `Reunión en N min · HH:MM` and its body the meeting title (the push payload gets an optional `body`, set only for meetings; `public/sw.js` shows it instead of the fixed line, and every other push is unchanged). A tap opens the Google Meet link when the event has one at `https://meet.google.com/…` (the only absolute URL a notification may open; `meetLink()`, and the worker re-checks it), otherwise the event in Mesa (`/calendario?dia=<day>`). A device holding a push subscription is told by the server and its page stays quiet (no double); the PC desktop notification needs an open Mesa tab and the permission, like every other desktop notification. Nothing is sent in the sandbox (no push notifier there) and the seeded events are samples.

## 9. Wake protocol and CLI

**Wake (long-poll):** the lead blocks on `mesa wait` (`GET /api/wait?session=lead`). The server answers as soon as there are events after the session's cursor (targeted or broadcast), or with `[]` after `timeout`.
- **Delivery is at least once.** `mesa wait` acks a batch after printing it (`--manual-ack` leaves it to `mesa ack <cursor>`), so a handler must check current state before it acts. Waiters inside a command (`ticket ask --wait`, `salida propose --wait-release`) poll with `peek=1`, which never acks. Events older than 7 days are pruned hourly. `docs/SESSIONS.md` is the session guide.
- **`ticket.created`** payload: `{ ref, ticketRef, taskId, kind? }`, targeted at `lead` for dispatched cards, Nuevo pedido and PR intake (`kind: review`, § 4). The lead triages by `kind` (TEAM.md § 4), claims, spawns the owner and records the team; handlers check the ticket first (at least once).
- **`ticket.pr_message`** payload: `{ ref, ticketRef, messageId, itemId, repo, pr, who, url, channelId, ts, threadTs }`, targeted at the PR ticket's owner session (`lead`): a Slack message about the PR (PR intake, § 4). The lead spawns or reuses `writer-<ref>` on that ticket, which classifies it: a notice gets `mesa item pr-notice <itemId>`, a question a salida to `channelId` + `threadTs`. Handlers check the ticket first (at least once); one wake per Slack message.
- **`ticket.batch`** payload: `{ batchId, origin: hoy|tablero|cli|github|slack, tickets: [{ ticketRef, taskId, title, kind?, urls }] }`, targeted at `lead`, sent instead of N `ticket.created` when 2+ new tickets open in one call (Hoy "Abrir tarea y pasar a Claude", Tablero "Dárselas a Claude"). The tickets are already open and owned by `lead`; the lead groups and routes them (`mesa-start` § 5, TEAM.md § 4 Batches). Handlers check every ticket first (at least once).
- **`ticket.answered`** payload: `{ ref, messageId, chosen, answers: [{ questionId, n, chosen, label, text }], openLeft }`, one per Andrés message. `answers` lists the questions that message answered (`chosen` null when he answered in words; `label` the option's label), `openLeft` how many stay open in the ticket. The lead relays the answers inline to the owner (`mesa-start` § 5).
- **`ticket.resumed`** (t126) payload: `{ ref, ticketRef, by: "andres"|"dependency", dependencyRef? }`, targeted at the ticket's owner session (`lead`): a paused or ongoing ticket came back to Claude (`waiting_claude`), because Andrés pressed "Reanudar" or because the ticket it was paused until closed (`dependencyRef`). Claude's own `mesa ticket resume` sends none. The lead relays `RESUMED <ref> by <by>` to the owner and respawns one if none is live; check the ticket first (at least once).
- **`ticket.checklist`** payload (t124): `{ ref, ticketRef, messageId, stepId, n, done, doneCount, total, allDone }`, one per real tick or untick by Andrés, targeted at the ticket's owner session. `done` is the new state of step `n`, `doneCount` / `total` count that checklist, `allDone` is true when the last step was ticked. Claude's own marks (`mesa ticket check`) emit none, and setting the state a step already has emits none. The lead relays it to the owner (`mesa-start` § 5, `ANSWER <ref> checklist <n> done|open <doneCount>/<total>`); the owner re-reads `mesa ticket context <ref>` (its `checklists`) for the states, and may mark a step it verified itself.
- **`ticket.annotations`** payload (t125): `{ ref, ticketRef, attachmentId, annotationIds, count }`, ONE per press of "Enviar a Claude (n)" in the PDF review view (never per mark, comment or keystroke), targeted at the ticket's owner session. `annotationIds` are the marks sent in this batch. The lead relays it to the owner (`mesa-start` § 5, `ANSWER <ref> annotations <attachmentId> <count>`); the owner reads them with `mesa ticket annotations <ref> --att <attachmentId> --open` (page, kind, `rect` in page units, `quote`, `body`, `replies`) and answers each with `mesa ticket annotation-reply <ref> <annId> --body -`; Andrés sees the reply in the panel live. `mesa ticket context` carries `annotations`: `[{ attachmentId, filename, open, total }]` per PDF that has marks.
- **Kinds:** `ticket.created|batch|answered|plan_approved|checklist|annotations|closed|reopened|resumed|permission_requested|pr_message`, `salida.turn|released|queued|undone|denied|delete_requested|restore_requested`, `review.action`, `sweep.requested`, `task.moved` (reserved; the UI gets task moves from `/api/stream`).
- **On `salida.released`:**
  1. `mesa salida show <id>`.
  2. If `recheckThread` is set, re-read the thread and `bounce` if it changed.
  3. Send `versions[approvedVersion-1].body` to exactly `destination`. Slack: by the event's `mode`, `draft` = one `slack_send_message_draft` (`channel_id` = `destination.channelId`, `thread_ts` = `destination.threadTs`), `send` = one `slack_send_message` with the same fields. Guardrail G5 passes each tool only for a released, unsent salida in that mode with exactly that text and target.
  3b. **Calendar** (source `calendar`): create the event with the Google Calendar connector's `create_event` using exactly the fields of `versions[approvedVersion-1].body` (title, start, end, time zone, invitees, Google Meet yes/no, description); guard G5 passes the call only when every field equals the approved ones, and refuses every other Google Calendar write. Then `mesa salida sent <id> --permalink <the event's link>`. In the sandbox report `--simulated` and never call the connector.
  4. Report with `mesa salida sent|drafted|failed|hold`. A failed draft call (a draft already in that channel, any tool error) is `hold --reason "<clear reason>"`, never a direct send.
- **On `sweep.requested`** (sent to the sweeper session, `MESA_SWEEPER_SESSION`, default `sweeper`): run the sweep for the listed sources now, ignoring `backoff_until`.

**Sweep tick (lane C):** the haiku sweeper runs about every 60 s per source in two stages. A cheap probe compares the source against `watermark`. When the probe finds something new, a full triage upserts items (`mesa item upsert`, deduped on `(source, external_id)`). The sweeper then writes back `watermark`, `lastChecked`, `lastNewAt`, `health`, and an adaptive `cadenceS`/`backoffUntil` with `mesa source set`: It backs off while a source is quiet or failing. It goes back to 60 s when something new arrives or when `lastInteractionAt` shows Andrés is active.

**CLI (`bin/mesa`, `bin/mesa.cmd`):** zero-dependency Node over the REST API.
- Env: `MESA_URL`, `MESA_SESSION`, `MESA_AGENT`, `MESA_TOKEN`.
- Output: JSON on stdout, errors on stderr (exit 1, usage exit 2). `--body -` reads stdin.
- Checklists (t124): `mesa ticket checklist <ref> --json -` posts `{"body": "...", "steps": [{"text": "...", "detail": "..."}]}` (a bare string is a step with no detail; `refs` optional) and `mesa ticket check <ref> <step> [--undo] [--note "<one line>"]` marks a step Claude verified itself (the CLI marker makes it `doneBy: claude`). `<step>` is a step id (`ck_…`), `<message id>/<n>` (sent as `<message id>.<n>`), or a bare `n` while only one of the ticket's checklists has that step (else 400 "ambiguous"); `ticket context` lists the steps. `--undo` does not take a note.
- PDF review (t125): `mesa ticket attach <ref> <file> [--message <id>]` uploads a file to the ticket (multipart to the attachments route, 25 MB) and prints the `Attachment`; a PDF gets a "Revisar" button in the thread that opens `/tickets/<ref>/pdf/<attId>`. `mesa ticket annotations <ref> [--att <attId>] [--open]` prints the marks as JSON (`id, attachmentId, page, kind, rect, geometry, quote, body, author, state, sentAt, replies`); `mesa ticket annotation-reply <ref> <annId> --body -` adds Claude's reply (the CLI marker makes the author `claude`).
- Commands (`node bin/mesa help` lists them all): `session`, `wait [--once|--loop]`, `ticket ask|reply|questions|question withdraw|checklist|check|plan|claim|close|pause|ongoing|resume|action|show|list|context|brief|handoff`, `handoff`, `handoffs`, `team add|join|retire|spent|list`, `finding upsert|list`, `review open|list|show|close`, `approval show`, `salida propose|version|sent|drafted|failed|hold|bounce|deleted|restored|withdraw|show|list`, `source get|set`, `calendar list|next|status|free|people|refresh|propose`, `sweep`, `task create [--note-only]|dispatch|list|move`, `item upsert|skip`, `engram link`.
- Missing on purpose: there is no approve (and so no Slack mode), schedule, deny, undo or "Ya lo envié" for salidas, and no decision for approvals. Those are Andrés's buttons. `salida withdraw` and `review close` are the lead's cleanup, not approvals: they never send and never count as his turn.

## 11. Security

- **Local first.** The server binds `127.0.0.1:8790` (`pnpm dev` and `pnpm start` go through `scripts/serve.mjs`; `MESA_HOST` overrides, and `0.0.0.0` is an explicit decision), so nothing on the LAN reaches the port. `src/proxy.ts` (policy in `src/lib/access.ts`) treats a request as local only when its Host is loopback AND it shows no sign of a proxy: none of `Cf-Access-Jwt-Assertion`, `Cf-Visitor`, `Forwarded`, `X-Real-IP`, `Via`, `CF-*`, and no `X-Forwarded-*` value that differs from what Next fills in for a direct connection (Host as host, a loopback client, `http`, the Host's port). Gotcha: Next 16 sets all four `X-Forwarded-*` itself on every request before the proxy runs, so their mere presence cannot be the test. The Host check is never a boundary on its own. `?token=` does not exist: the token never travels in a URL.
- **Phone access: Cloudflare Tunnel + Cloudflare Access, two keys.** A named cloudflared tunnel (`MESA_CF_TUNNEL`, default `mesa`) maps `MESA_PUBLIC_URL` (https://mesa.<his domain>) to `http://127.0.0.1:8790` with a catch-all 404 (`pnpm tunnel up` writes the config to `~/.cloudflared`, never into the repo, and holds no credentials). A Cloudflare Access app on that hostname lets only his email in (suggest a 30-day session). **Key 1** is the Access JWT, verified by Mesa itself, not trusted from the header's presence: `src/lib/cf-access.ts` takes `Cf-Access-Jwt-Assertion` (or the `CF_Authorization` cookie), checks the RS256 signature with WebCrypto against `https://<MESA_CF_ACCESS_TEAM>/cdn-cgi/access/certs` (keys cached 10 min, refetched at most once per 30 s on an unknown `kid`), `iss` = the team URL, `aud` contains `MESA_CF_ACCESS_AUD`, `exp`/`nbf`, and `email` = `MESA_CF_ACCESS_EMAIL` (case-insensitive). It fails closed: any missing variable, unreachable keys or failing check is a 403, public paths included. No new dependency; the proxy runs on the Node runtime. **Key 2** is the `MESA_TOKEN` cookie (401 without it), required everywhere except the public shell and `/pair`. The phone gets the cookie from `/pair`: `POST /api/pairing` (PC only) mints one pairing: a long code (32 random bytes) in the QR link `MESA_PUBLIC_URL/pair?c=<code>` and an 8-character short code (alphabet without 0/O/1/I/L) shown next to it; both are the same single use, expire in 10 minutes, and only their SHA-256 is stored (`phone_pairings`). A page load that passes Access but has no cookie gets a small Spanish page with a field for the short code (`POST /pair`; an installed iOS app may not share Safari's cookie jar, so pairing has to work inside it). 5 wrong tries in 10 minutes block redeeming (429; `pair_failures`). `/pair` sets `mesa_token` (httpOnly, Secure, SameSite=Strict, 30 days). The token is never shown, copied or put in a URL or chat. `pnpm tunnel status` probes `https://<host>/` with no credentials and requires Cloudflare Access to answer (redirect to `cloudflareaccess.com`, or a Cloudflare 403); if Mesa answers (its `x-mesa-guard` header, a Next.js response, a 2xx) it exits 3, `up` refuses to start (and stops a tunnel it started), and mesa-start treats exit 3 as a stop.
- **One-time setup, all `needs_ok`, done with Andrés in this order:** (1) install cloudflared; (2) `cloudflared tunnel login` with the Cloudflare account that owns his domain (not Designli's); (3) `cloudflared tunnel create mesa`; (4) **create the Access app for `mesa.<domain>` (one policy: his email; session 30 d) BEFORE the DNS route**; (5) `cloudflared tunnel route dns mesa mesa.<domain>`; (6) put `MESA_PUBLIC_URL`, `MESA_CF_ACCESS_TEAM`, `MESA_CF_ACCESS_AUD`, `MESA_CF_ACCESS_EMAIL`, `MESA_TOKEN` in `.env.local` and restart Mesa; (7) `pnpm tunnel up` (or install the Windows service with the generated `~/.cloudflared/<tunnel>-mesa.yml`); (8) `pnpm tunnel status` must exit 0. After that the tunnel needs no manual step: see **Tunnel autostart**. No Cloudflare API token is ever stored in the repo.
- **Tunnel autostart.** With `MESA_PUBLIC_URL` and `MESA_CF_TUNNEL` set, `pnpm start` (`scripts/serve.mjs start`) also runs the tunnel, as a CHILD of that process (`scripts/lib/autostart.mjs`, no detached process): once the server accepts connections on `127.0.0.1:8790` it looks up the tunnel (`cloudflared tunnel list`), checks the credentials file, and probes the public URL without credentials. Mesa answering without Access means nothing is started, and a tunnel that is already running (service, `pnpm tunnel up`) is stopped. A tunnel that already has connections is reused, not doubled, and is not stopped with the board. Otherwise it writes the same `~/.cloudflared/<tunnel>-mesa.yml` as `pnpm tunnel up`, spawns `cloudflared tunnel --config ... run <tunnel>`, writes the pidfile, probes up to 10 times, and stops the child (one log line) if Mesa ever answers without Access. The child is killed when the server exits (SIGINT, SIGTERM, SIGHUP, normal exit, `process.on("exit")`); a hard kill of the Node process (`taskkill /F`) cannot run hooks on Windows and leaves cloudflared running, which the next start reuses, and `pnpm tunnel down` stops. cloudflared missing, not logged in, tunnel or credentials absent, or an early exit: one `tunnel: ...` log line and the board keeps running. `pnpm dev` does not start it unless `MESA_TUNNEL=on`; `MESA_TUNNEL=off` disables it everywhere.
- **PWA under Access.** `/manifest.webmanifest` (a route handler, `src/app/manifest.webmanifest/route.ts`), the icons (`scripts/make-icons.mjs`, drawn from the BrandMark), `sw.js` and `offline.html` need no Mesa token (they hold no data) but, like everything else, they need the Access JWT. A browser fetches `<link rel="manifest">` without cookies unless the link says `crossorigin="use-credentials"`, and Access would answer that fetch with its login redirect and break installability; `src/app/layout.tsx` therefore emits the link itself with `crossOrigin="use-credentials"` (Next's own manifest convention does not, so the file convention is not used). Same-origin icon and `sw.js` requests carry the `CF_Authorization` cookie. Fallback if a phone still cannot fetch an icon: an Access Bypass policy limited to exactly the public paths (`/manifest.webmanifest`, `/sw.js`, `/offline.html`, the four icons), which hold no board data. The service worker (`public/sw.js`, scope `/`, production builds only; dev unregisters it) precaches only that shell (one file at a time, so an expired Access session does not fail the install), caches `/_next/static/*`, answers navigations network-first and falls back to `offline.html` ("Sin conexión con tu PC", actions disabled) when the PC does not answer (network error, timeout, 502/503/504/530); it never caches `/api/*` or any HTML with board data and never queues a write. The install banner uses `beforeinstallprompt` where the browser fires it (Chrome, Edge) and a written guide otherwise: iOS Safari always, and on a phone-sized window any browser whose event has not arrived after about 3 s (Opera and Samsung Internet never fire it, Chrome sometimes does not), worded for the browser read from the user agent (`src/features/phone/install.ts`: Opera, Samsung Internet, Chrome and other Android; iOS has Compartir → Agregar a inicio). The native button replaces the guide if the event arrives late. Hidden when standalone and for 14 days after a dismiss. `/telefono` always has an "Instalar en el teléfono" section with the steps for this browser (all of them on the PC), a way to show a dismissed banner again, and a readout of the install state (browser, installed, prompt, dismissed, secure context, service worker) so a "no me sale" can be read off the screen. The phone strip shows "vía túnel", "sin túnel", or "Vuelve a entrar" (with an Entrar button that reloads into the Access login) when the health ping is redirected to Access or refused (403).
- **Phone layout.** The tab bar is thin: `--phone-tabs-h` is 54px of content plus `env(safe-area-inset-bottom)` (`src/styles/tokens.css`), so everything anchored to it follows. Its last tab, "Más", opens the Ajustes sheet (`src/components/shell/SettingsSheet.tsx`, on the shared `Sheet`: closes with Esc, a tap outside or back) with the controls the desktop rail keeps in its foot, reusing the same components (Teléfono, NotifyToggle, SoundToggle, ThemeToggle, Hecho hoy, `SourceHealthList`); the theme persists in `localStorage` exactly as on desktop. Inside a ticket the header (back, title, status; `.tk-phead`) is sticky at the top while the page scrolls, under the safe-area inset and never over the sticky composer.
- **Build version.** `scripts/serve.mjs` hands Next `MESA_BUILD_SHA` (short git sha) and `MESA_STARTED_AT`, `GET /api/health` returns `version: { sha, startedAt }` (`src/lib/version.ts`), and it changes on every merge and every restart. Every screen (`src/features/version`) remembers the version it loaded and compares on each 30 s check while visible, on `visibilitychange` and on `online`; when it differs a quiet "Hay una versión nueva · Recargar" appears, and Recargar runs the service worker's `registration.update()` and reloads. Nothing reloads by itself, so a draft is never lost. `/telefono` shows "Versión <sha> · <fecha>".
- **The calendar feed address is a secret** (t112). `MESA_GCAL_ICS_URL` lives only in `.env.local` (`.env.example` lists the name). It is read by `feedConfig()` and used by `fetchFeed()` and by nothing else: not stored in SQLite, not in `source_state`, not in any log, error, API response, wake event or ticket (every failure is a fixed phrase: `Google no entrega el calendario (HTTP 403)`, `sin conexión con Google`, `Google no respondió a tiempo`, …; tests assert the address appears nowhere). The poller never starts in the sandbox, and a value that is not an `https` URL is reported as invalid without echoing it. Anyone holding the address can read the calendar: rotate it in Google Calendar if it leaks.
- **No secrets in the repo, and no Slack or Basecamp credentials at all.** Those connectors live in Claude's MCP, and GitHub uses the `gh` login. `.env.local` (gitignored) holds only Mesa settings, which `.env.example` lists. `data/` and `*.db` are gitignored.
- **Every outgoing write needs Andrés's explicit approval of the exact text and destination.** Slack and Basecamp messages and GitHub reviews/comments are salidas, and the review buttons approve the exact text shown on the card. Mesa refuses `sent` and `drafted` before the 20 s undo window ends. For Slack the approval click also picks the mode: Aprobar leaves a draft Andrés sends himself; "Aprobar y que Claude lo envíe" sends through the connector with its "Sent using @Claude" footer.
- **Permission approvals allow one call at a time.** Allow comes only from an explicit "Dar permiso" before expiry. Everything else is deny, and the hook never emits `updatedPermissions`. The one standing rule Mesa ever writes is the "Permitir esta regla" of a denied-call card (§7b): derived by the server, one worktree directory, appended by the server and never by Claude.
- **Approval rules are only partly enforced by the API.** The local API does not authenticate callers, so "sessions and agents never approve, schedule, deny, undo or decide" rests on CLAUDE.md, guardrail G10 and on the CLI having no such commands. What holds: the only routes that decide an approval are the UI's approve / read-config / deny (decidedBy `andres`), and the hook honours a decision only with `decidedBy` `andres` (anything else is a deny). What does not: those three routes have no credential, so any local process (a script, browser automation, or a shell shape G10 misses) that calls one counts as Andrés. G10 is partial (literal loopback host and port, curl-style tools only; it misses `$MESA_URL`, other host spellings, doubled slashes, quoted or spliced segments and disguised tool names, see docs/TEAM.md section 6), and it also covers `permission-request`. That is the known residual risk until improvement 13; hardening is on hold.
- **Uploads** are stored under `data/uploads/<ticket>/` with sanitized names and a 25 MB cap.
- **Sample data is labelled** (`is_sample`) and shown with "Datos de muestra.".

## 12. GitHub, server side (lane C)

`src/lib/integrations/github-worker.ts`, started from `src/instrumentation.ts`. It runs with Andrés's `gh` login (the token is read from gh's keyring for `MESA_GH_USER`, default `acorrea-designli`, and passed only to the child process; nothing is stored). It is enabled when `MESA_GITHUB=on`, or when neither `MESA_GITHUB` nor `MESA_DB` is set (the real board). Dev servers on scratch databases stay off GitHub unless they opt in.

- **Notifications** (`github-ingest.ts`): `GET /notifications` with `If-Modified-Since` (the last `Last-Modified`, kept as `source_state.github.watermark`), never sooner than `X-Poll-Interval` (floor 60 s, kept as `cadenceS`). A 304 costs nothing.
- **Review requests**: REST search `is:pr is:open review-requested:@me` (GraphQL is left to pr-monitor), when the notifications changed, every 5 minutes, or on `POST /api/github/sync`. Each non-draft PR is an item `{source: github, externalId: pr:<owner>/<repo>#<n>, kind: pr_review, need: approve_pr, project: <owner>/<repo>, excerpt: "+120 −34 · sin revisar"}`. Details (`+/−`, Andrés's last review) are fetched only when the PR's `updated_at` moved. A request that disappears from a complete search moves its item to Hecho; one that comes back returns to the inbox. With `autoDispatch` on, a new request and a re-request also get their review ticket (PR intake, § 4); `ReviewSyncResult.intake` reports `{ created, reused, reopened, batchId }`. Items are matched case-insensitively by key. A release-train PR (title `Create staging|prod|production PR` with both branches in develop, staging, main, master, production, prod; the auto-created one approved at deploy time) is never an item: only a matching title costs the extra branch read (same `pulls/<n>` GET), the PR is not `seen` (an older item moves to Hecho) and `skippedRelease` counts it.
- **Health**: success sets `github` ok; a rate limit sets degraded with note `límite de API · HH:MM` and waits for the reset; auth or a missing `gh` sets down.
- **GitHub Project** (`github-project.ts`): the private Project "Mesa" owned by `acorrea-designli`, created only when missing. Its Status field carries Inbox, Todo, In Progress, Waiting, Done (existing option ids are kept). Settings: `gh_project.id`, `.number`, `.url`, `.owner`, `.status_field_id`, `.status_options` (name → option id), `.known_items`, `.last_pull_at`. Push (every 5 s when there are pending tasks): a task without `gh_item_id` becomes a **draft** item (`gh project item-create`: title, then a body with the excerpt, `Proyecto: <project>`, the linked PR or issue URL as plain text and `Mesa: <taskId>`); then its Status is set and `markSync(synced)` clears "Sin sincronizar". A task moved again while the write was in flight stays pending. Write errors mark the task `error`; a missing `project` scope sets `github_project` down ("sin permiso": run `gh auth refresh -s project`). Pull (every 2 min): a Status changed in GitHub moves a synced task and its items; a pending local move wins until acked; draft items added in GitHub become tasks once (items of tasks deleted in Mesa are never re-imported); PR and issue items added by hand are counted (`skipped`), recorded in `.known_items` and never imported nor edited. **Drafts only, never linked content:** Mesa never adds a PR or issue to the Project (`item-add` / `addProjectV2ItemById` link a client PR and write a timeline event on it at every card move). `guardProjectGh` refuses those calls (and `linkProjectV2*`) with a thrown error before gh runs, `gh_content_url` stays null for items Mesa creates, and migration `0320` cleared the content links the earlier mirror left (those tasks got a fresh draft). Sample tasks never leave Mesa.
- Mesa never writes PR reviews or comments: those are salidas the lead sends.
- **Sandbox** (`MESA_ENV=sandbox`, `docs/SANDBOX.md`): the worker never starts and `POST /api/github/sync` answers 409 `sandbox`.

## 13. Claude usage (t45, redrawn in t60)

Two sources feed the `Uso` block of the rail foot and the Ajustes sheet (phone: two meters, one link) and the `/uso` screen (`src/app/uso`, `src/features/usage`): the plan windows as meters with a pace tick plus a "% used over time" chart each, then tokens for Hoy or Semana (tokens nuevos, ranked by role and by model, the week by day, and a table view). `/semana` no longer carries the tokens.

- **Plan limits (% remaining).** Claude Code passes the statusLine command a JSON on stdin with `rate_limits.five_hour` and `rate_limits.seven_day` (`used_percentage`, `resets_at` in epoch seconds; undocumented, and absent for API-key sessions). `scripts/statusline.mjs` prints `<model> · 5 h N% restante · semana N% restante` and POSTs the figures to `/api/usage` on the loopback Mesa it is pointed at (`--url`, else `MESA_URL`) with a 1.5 s timeout; it prints first and always exits 0, so a Mesa that is down changes nothing. It posts nothing when `rate_limits` is absent, so a good snapshot is never overwritten. It reads no credential and calls no Anthropic API. The figures are account-wide and refresh only while an interactive session (the lead) is open: the rail dims a snapshot older than 15 min and reads "sin dato" when there is none. A window whose reset time has passed also reads "sin dato". Each accepted POST also appends a point to `usage.history` (`pointOf` / `appendPoint` in `domain/usage.ts`), which `chartSeries` cuts to the current window for the /uso charts; the history starts at the deploy, so the charts fill over hours.
- **Tokens spent.** `transcripts.ts` reads the Claude Code transcripts of this board's sessions folder (`<CLAUDE_CONFIG_DIR or ~/.claude>/projects/<slug of the folder>`; the folder is the parent of this repo, or its `designli-sandbox` sibling on the sandbox board; `MESA_SESSIONS_DIR` and `MESA_TRANSCRIPTS_DIR` override). The lead's `<session>.jsonl` counts as `lead`; each `<session>/subagents/agent-<id>.jsonl` takes its role from the sibling `.meta.json` (`agentType`, else the description's name: sweeper, tl, dev, reviewer, writer, otherwise `other`). Only the assistant `message.usage` is read. The scan is incremental (a byte offset per file, complete lines only, one response counted once however many content blocks repeat it), skips files untouched since before last week, runs at most every 30 s and is kept in `settings`, so a restart never starts over. `domain/tokens.ts` buckets by Bogota day and sums today and the week (Monday to now). "Tokens nuevos" is input plus cache writes plus output; rows are ranked by it, and cache reads are shown once, apart. In the table view Entrada is fresh input plus cache writes, Caché is cache reads, Salida is output. `weekDays` gives the Monday-to-Sunday series.

`scripts/install-team.mjs` adds the statusLine to `<target>/.claude/settings.json` only when the file has no `statusLine` at all (never replacing one that is there), pointing at `:8790` for the live folder and `:8796` with `--env sandbox`. Andrés runs it himself (`docs/TEAM.md` § 9) and reopens the session.

## 14. Calendario (t112)

Andrés's Google Calendar on the board: a screen (`/calendario`, in the rail and on the phone's tab bar), a "Próxima reunión" strip (Calendario, Hoy and the phone), a free-text way to ask Claude for a meeting, and reminders ten minutes before each one (§ 8, "Meeting reminders"). Reading is Mesa's; writing is a salida.

- **Reading: a private iCal feed, polled by the server** (`src/lib/integrations/calendar-worker.ts`, started from `src/instrumentation.ts`). It runs only when `MESA_GCAL_ICS_URL` is set (Google Calendar > Settings > the calendar > "Secret address in iCal format"), never in the sandbox, and not when `MESA_CALENDAR=off`. Cadence 5 minutes (a 30 s timer decides when it is due); each failure doubles the wait (10, 20, 40, then 60 minutes) and the read can be retried at any time with "Actualizar" (`POST /api/calendar/refresh`). Health is the `source_state` row `calendar`: `ok` after a good read, `degraded` after one or two failures, `down` from the third (and for an address that is not https), with a fixed Spanish note and the last good read (`lastNewAt`); the rail lists "Calendario" in its Fuentes block once it has reported and something is wrong, and the Calendario header pill shows "Google Calendar · leído hace N min" or, when it fails, a dashed "Última lectura HH:MM" with the stored events still shown (reminders keep working from them). Google Workspace can block the private address (HTTP 403/404): the note says so, and the fallback is to ask Andrés for another way (OAuth or an MCP read), not to guess. A `down` calendar never parks a calendar salida in "Aprobar al volver": reading is not creating (`sourceDown()` ignores it).
- **The reader** (`src/lib/domain/ics.ts`, pure, tested): folded lines; DTSTART/DTEND/DURATION in UTC, floating, `TZID` (IANA) and `VALUE=DATE`; `RRULE` DAILY, WEEKLY, MONTHLY and YEARLY with INTERVAL, COUNT, UNTIL, BYDAY (with ordinals), BYMONTHDAY, BYMONTH and WKST, expanded in the event's own zone so a 09:00 meeting stays at 09:00 across a DST change; EXDATE and RDATE; `RECURRENCE-ID` overrides (a moved occurrence keeps its original start as `occurrence_key`); `STATUS:CANCELLED` is dropped; the attendee line whose address is the owner's (`MESA_GCAL_OWNER_EMAIL`, else `X-WR-CALNAME` when it is an address) gives `response`, so declined meetings are known; the Meet link comes from `X-GOOGLE-CONFERENCE`, then the location or description. Not handled (an event keeps only its first occurrence): BYSETPOS and rules finer than daily. An unreadable event is counted (note: "N evento(s) ilegibles") and skipped, never fatal. All-day events are drawn from Bogota midnight to Bogota midnight.
- **Time.** Everything is shown in Bogota (UTC-5), like /semana. Stored times are UTC ISO.
- **The screen** (`src/features/calendar`, variant A of `.impeccable/mocks/screens/calendario.md`): the header with the health pill and "Actualizar"; the strip; the week as a line band (one station per day; today and the past in full line, what lies ahead at about 35%; a count in each capsule; a day is a link, `?dia=YYYY-MM-DD`); a week switch above the band (t127: "Semana anterior", "Esta semana" and "Semana siguiente" are links that move `?dia=` by seven days and keep `vista`; the label says the week, "10–16 nov", and whether it is the current one; a week or day outside the stored window shows one line saying so and a link to that week in Google Calendar, `https://calendar.google.com/calendar/r/week/Y/M/D`, never an error); "Hoy" and "Semana" tabs (`?vista=semana`) over the agenda rows (hora, reunión, personas, "Unirse" to the Meet link and, on every row, "Abrir en Google" (new tab, `rel="noopener noreferrer"`; read only, nothing is written to Google); the next row is lined in the Calendario colour; a declined meeting is a dashed "Rechazada" and is never reminded; an all-day event says it does not remind); and the 392 px pane "Pedir reunión". Without the feed the screen says "Calendario sin conectar" (it names `.env.local`, never the address) and Hoy shows no strip; in the sandbox it says "Sandbox: sin lectura de Google" unless sample events are seeded, which then show with "Datos de muestra.". The rail count is the meetings left today (`Counts.calendar`). The colour is the fifth line, `--ca` (DESIGN.md).
- **Asking for a meeting.** "Pedir a Claude" posts his words to `POST /api/calendar/requests`, which opens an ordinary `andres_asks` ticket for the lead (title `Reunión: …`, body marker `Pedido de reunión (Calendario)`); the pane lists his recent requests with their ticket and, when it exists, the pending calendar salida. The lead handles it like any request (`mesa-ticket` skill, "Meeting requests"): it reads `mesa calendar free --day <day> --minutes <n>` for a free slot (from the stored events) and `mesa calendar people` for the invitees' addresses, and proposes the exact event with `mesa calendar propose --title … --start <ISO with offset> --end … --invitee … [--no-meet]`, which creates the salida (source `calendar`). Where a guest's address cannot be found it asks Andrés in one question card instead of guessing.
- **Creating.** Every event, with or without invitees, is a salida (decision 4A): the card shows the exact event (title, when, zone, invitees, Meet), the chips "Tu calendario principal", "Google Meet" and "Invita a N personas" in the Calendario colour, and the usual Aprobar, Editar and Denegar with the 20 s undo. On `salida.released` the lead creates it with the Google Calendar connector's `create_event` (hook G5 compares title, start and end as instants, invitees as a set, Meet and description with the approved body and refuses any difference, any parameter the approved event does not cover (recurrence, reminders, location, `sendUpdates`, a second alias for the same field, a time zone or `calendarId` different from the approved one; an empty alias never hides a second one, and an unknown parameter set to `false` still counts) and any other Google Calendar write, while the connector's own sign-in (`authenticate`, `complete_authentication`) and reads pass; a teammate can never write; the sandbox lets nothing out) and then reports it sent with the event link (`--permalink`). Whether the connector can attach a Meet (`conferenceData`) is unverified until Andrés authenticates it (plan action 1): the parameter names the guard reads are tolerant (`summary|title`, `start|startTime`, `attendees|guests`, `addGoogleMeet|conferenceData|…`), and if the connector cannot add a Meet the salida is proposed with `--no-meet` or held with a clear reason. In the sandbox the report is `--simulated`.
- **Moving** (t131). Moving an existing event is a calendar salida whose body starts with `Mover: <eventId>` (then `Título`, display only, `Inicio`, `Fin`, `Zona`, `Avisar: sí|no`; `src/lib/domain/calendar-move.ts` and its twin `scripts/hooks/calendar-move.mjs`; `create` and every new version accept an event body or a move body and refuse anything else, and a create-only field in a move is a 400). On `salida.released` the lead calls the connector's `update_event` (or `patch_event`); hook G5 passes it only for a released, unsent, non-sample move salida with the same eventId, calendar (`primary` by default), and start and end as instants, read as strict local times (`YYYY-MM-DDTHH:MM[:SS]`, no offset or Z, as the connector reads them) in `timeZone`, which is required and must equal the approved Zona, and refuses any parameter beyond `eventId`, `calendarId`, `startTime`, `endTime`, `timeZone` and `notificationLevel` whenever it is present, even empty or `false` (an empty field can clear one on the client's event), a missing start or end, and a `notificationLevel` that contradicts `Avisar` (sí: `ALL` or absent; no: `NONE`). Delete, respond and calendar changes stay refused.
- **Sample data.** `seedSamples()` adds a fictional week of meetings (`is_sample`, shown with "Datos de muestra.") and one pending calendar salida; the sandbox reset keeps those events as samples (it never fetches), while the salida becomes ordinary like every other seeded one.
- **Hook rollout.** `scripts/install-team.mjs` adds `mcp__claude_ai_Google_Calendar__.*|mcp__google-calendar__.*` to the rails hook matcher and widens the matcher of an existing install (never narrows it): run it again after merging (docs/TEAM.md § 9), in the live and the sandbox folders.
